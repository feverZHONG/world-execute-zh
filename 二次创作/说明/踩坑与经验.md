## 一、五条用血换来的工作法

1. **接口先实测，不推断。** 这工程最容易翻车的地方都在"看起来显然"的地方：`Image` 能不能 decode SVG、SVG 的固有尺寸是多少、ffmpeg 支不支持某个选项。实测代价是几秒，猜错的代价是整轮返工。
   —— SVG 那次实测：只写 `viewBox` 的图，Chrome 给的固有尺寸是 **113×150**，不是 viewBox 尺寸。
2. **改完立刻单帧取证，日志干净不等于画面对。** 1280×720 抽一帧、`--cols 1`、逐张 `Read`。工程不报错的地方最容易歪（控件位置全归零、文字压字、构图偏移都不报错）。
3. **判断"到底换没换"，用哈希和 PSNR，不用眼睛。**
   `Get-FileHash` 对比两张 4K 静帧 → SHA256 完全相同，才发现 SVG 根本没被用上（服务端 MIME 缺 `.svg`，浏览器拒解码后静默回落 PNG）。
   `ffmpeg -i a.png -i b.png -lavfi "[0:v][1:v]psnr" -f null -` → PSNR 是判断"改了之后画面动没动"的量化尺子：inf = 逐像素相同；37–42 dB = 只有边缘重采样差；11 dB = 结构变了（构图错位）。
4. **动中文之前先跑字表，动完再导出。**
   `node tools/zh_charset.mjs` → 再 `node tools/zh_charset.mjs --check`（退出码 0）。漏一个字的代价是导出时 `[text] glyph outside the bundled fonts and their CJK fallback in "已记录" (... U+5F55 in sans)`，整帧作废。
5. **任何"尺寸/基准"变化，先把写死的基准清点出来，再把换算收进一个文件。**
   本工程把 **1086×1448** 当设计单位写进了场景里（裁切矩形、归一化分母、图框宽高比）。清点完是把换算收进 `art.js`（`REF` + `_src/_dgn`），**不是**把换算摊进十几个场景——摊开就是把一处风险改成十几处。收口方式与验证法见 3.3。
   推论：改完先证"没改坏"（同尺寸逐像素一致），再证"改好了"（换尺寸不错位）。两个都要，少一个都不算验完。

## 三、美术层

### 3.1 素材本身的事实（渲染器怎么吃图）

- 八张图是**三墨剪影**：`INK_RGB` 种子 `#f4e0c6` / `#dc723f` / `#241a15`，载入时按每图实心像素质心再修正一次。
- `_prepareInk` **每次载入只读一次像素**，之后全片只做裁切/上色/遮罩/网点/描线，不再读像素。
- 分墨规则：`alpha<16` 当尘埃丢弃、`alpha>=250` 当实心补成 255、`0..128` 的软边取最不透明邻域的分墨；墨与墨之间按"到两墨混合线的投影"分配；`f_reach` 的第四种锈色被折进黑。
- 三块版是**累进**的（cream → orange → black，低版压在高版下面），所以错版时露出来的是下面的墨，不会出现接缝。
- **设计单位 vs 源像素**：全片所有数字（`regions.json`、裁切矩形、`/1086`、`REGISTER` 位移）都按**设计基准**理解（八张 v4 原尺寸，`art.js` 的 `REF` 表），`art` 对外收发设计单位，内部才用源像素。详见 3.3。
- `REGISTER` = `p' = s·p + [tx,ty]`，位移是**设计 px、以 1086 宽的 `f_bust` 为准**；`fit()` 里 `k = base.w / (f_bust.ref.w)`，所以换大图后这张表不用重测。
- `MAX_UNTREATED = 1.75`：4K 下源放大超过 1.75 倍就改画路径（`inkPath`），所以特写是"描出来的矢量"而不是放大位图。`LUM_H = 240` 是网点/字符屏的工作分辨率。

### 3.2 坑

| 现象 | 根因 | 修法 | 证据 |
|:--|:--|:--|:--|
| 没法在 Node 里量 PNG | 依赖只有 `ffmpeg-static` 与 `playwright-core`，没有 pngjs/sharp/jimp/canvas | 借工程自带的 `export\server.mjs` 起静态服务，无头浏览器 `createImageBitmap` 解码；不渲染任何一帧 | `tools/art_check.mjs` |
| 换图后不知道"偏没偏" | 没有基线可比 | `docs/archive/v4/art/baseline.json` 记八张的包围盒/尺度，`art_check` 比位移与尺度差（>5% 判必须处理） | 同上 |
| `--artsvg` 传了但画面没变 | `server.mjs` 的 MIME 表没有 `.svg`，浏览器把 SVG 当二进制拒解码 → 静默回落 PNG | 补 `'.svg': 'image/svg+xml'`（同时补了 `.jpg`） | 两张 4K 静帧 SHA256 相同 |
| SVG 烘焙后整张作废 | SVG 只写 `viewBox` 不写 `width`/`height`，Chrome 固有尺寸回落成 113×150 | `loadArt` 现在自动从 `viewBox` 补 `width`/`height`，并 warn「不足 1.5× 设计基准」；规格单仍要求画师写全 | 实测 `naturalWidth=113, naturalHeight=150`；补完后 `tools/art_dims.mjs` 量到 1086×1448 |
| 换成更大的图/矢量图，构图整体错位 | 场景把 1086×1448 当设计单位写死（`HAND_CROP`、`band`、`/1086`、图框宽高比） | **已修**：坐标基准收进 `art`（`REF` 表 + `_src`/`_dgn`/`_full` 换算），场景一个数都没改 | 修前 170.19 秒 PSNR **11.16 dB** → 修后 **38.5 dB**；同尺寸回归三张静帧 SHA256 与改前**完全相同** |
| 以为矢量化能提升画质 | 位图矢量化不增加信息，只是把同一条边重画得更细 | 想真吃矢量收益，画师得按矢量画（或画得更大）；基准已参数化，矢量版才可能不偏 | 同尺寸 PSNR 37.4 dB；3000 烘焙 PSNR 42.5 dB（边缘略顺，无新细节） |
| 现有素材的 alpha 不可信 | 主体是 253/254 不是 255，外侧还有 1–2% 的 `alpha<16` 残点（带红带白） | 渲染器兜底；新图按规格单必须 255/0 | `art_check` 实测表 |

### 3.3 坐标基准：口子怎么收、怎么证明没改坏

**问题**：片子里每个数字都是 1086×1448 坐标系里的（裁切矩形、`/1086`、`/1448`、图框宽高比）。源图一放大，这些数字全变成"错的但依然合法"，报错没有、画面整体偏。

**收口方式**（`src/engine/art.js`）：

- `REF` 表写死八张的设计基准（七张 1086×1448、`f_eye` 1254×1254），装载时算一次 `sx = 源宽/基准宽`、`sy = 源高/基准高`。
- 对外 API 收发**设计单位**：`crop`、`cover(focus)`（返回值也是设计px）、`part(seed)`、`halftone/silhouette/ascii` 的 `crop`、`inks/inkClip/partClip` 的 `crop`。内部一律先 `_src()` 换成源像素，再碰 mask/路径/位图。
- `region()` 原样返回 `regions.json`（设计px）；`REGISTER` 与 `fit()` 按 `f_bust.ref.w` 换算。**换图后这些文件与场景都不用改。**
- 坐标换算只发生在 `art.js` 一个文件里，场景保持"设计单位 + `/1086`"的老写法——这一条很重要：把换算摊到场景里，等于把一处风险改成八处。

**验证法（两次都必须做）**：

1. **同尺寸恒等回归**：现有八张尺寸恰好等于基准 → 所有换算退化成乘 1，重渲染应与改前逐像素相同。实测 `out/reg_chorus.png`、`out/reg_shut.png`、`out/reg_alone.png` 与改前的 `qa_chorus/qa_shut/qa_alone_count.png` **SHA256 完全一致**。
   —— 注意：`qa_drawer_alone.png` 是双格 1280×1446（参数对不上），不能当基线；对不上先怀疑"当时用了别的参数"，别先怀疑代码。
2. **换尺寸不错位**：`--artsvg assets/character_svg` 在 3840×2160 下跑 166.5 / 170.19 两秒，PSNR 42.5 / 38.5 dB。错位会掉到 11 dB 量级，这个量级一眼能分辨。
3. 顺带新工具 `tools/art_dims.mjs`：一次量完八张的 源尺寸 / 设计基准 / `sx`/`sy` / 长宽比偏差，`sx != sy` 或偏差 >2% 就是要出事。

**下次要小心的**：

- `f_eye` 是 1:1，别把它算进 3:4 的基准里（`REF` 表已经单独给它）。
- 新图比例若与基准不同（例如把 3:4 画成 4:5），`sx != sy`，每处裁切都会被拉扁——这不是坐标基准能兜的，必须退回画师重画。
- 基准是**构图基准**：脚本只保证"数字还指向同一个地方"，指的地方对不对要看画面（`art_check` 的位移/尺度差、肉眼并排）。

### 3.4 Live2D 顶替剪影：一轮实测（2026-11-17，结论：能跑通，不能当成品）

**问题**：八张剪影等画师，眼下想先用现成素材看效果。手上有《双生视界》高奈利亚的 Live2D 模型包（24 套服装，每套 `.moc3` + `.model3.json` + `textures/texture_00.png` 2048×2048 图集 + `motions/*.motion3.json`）。

**不用自造渲染栈**：`D:\GameMods\NekoMimi\tools\live2d_lib\` 已有成套 Cubism 运行时（`live2dcubismcore.min.js`、`pixi.min.js`**必须是 6.x**（`pixi-live2d-display` 0.4.0 只兼容 6.x）、`pixi-live2d-display.min.js`，同目录还有参考实现 `live2d_render.py`）。把它复制到 `tools/live2d_lib/`，自写 `render.html`（`?model&w&h&pad&zoom&ox&oy&motion&t&params&dump`）解决"要什么姿势就渲什么姿势"：

- moc3 是 **v3**，走 cubism4 core（不是 cubism3）。
- 模型没有可用 motion 时只能渲默认静止姿势；要别的姿势得自己解析 `motion3.json` 的 Segments 做定格，或直接写参数。
- 锚点必须 `anchor(0.5,0.5)` 再对画布中心，否则人物整块偏出。
- 参数名是**游戏自定义的大写**（`PARAM_ANGLE_X/PARAM_ANGLE_Z/PARAM_LEFT_ARM/PARAM_HAND_L/PARAM_TERE/...`），标准 Cubism 那套名字在这里不认。实测默认姿势：`ANGLE_X=-30`、`ANGLE_Z=-15`（头是偏的）、`HAND_L=2`、`HAND_R=1`。
- 每套模型画布 1500–1884 见方（实测 l2d16 为 1884×1884），4096 画布要 `pad 0.92` 上下留白。

**工具**：`tools/live2d_art.mjs` 两个子命令——`render`（moc3 → 透明 PNG，4096×4096 一张约 4.6 MB，80–90 s）与 `ink`（三墨化 + 清理 + 黑边 + 裁切）。

| 现象 | 根因 | 修法 | 证据 |
|:--|:--|:--|:--|
| `core.getParameterId()` / `core.parameters` 不存在 | pixi-live2d-display 的封装类只暴露 `_parameterIds` / `_parameterValues` / `_model` | 侧写 `core._parameterIds/_parameterValues` 遍历，或 `getParameterIndex` + `getParameterValueByIndex` | `out/_ref/dump16.txt` 的 PARAMS 行 |
| `OffscreenCanvas.toDataURL` 不是函数 | 只有 Worker 侧 Canvas 没有 `toDataURL` | 换 `document.createElement('canvas')`（`probe.html` 是同源页，能 `fetch` 工程内图片） | 报错原文 |
| 脚本跑完不退出，进程吊死 | 静态服务的 `server` 没关，Node 事件循环一直有活 | `finally` 里 `browser.close()` + `server.close()` | 第二次运行即返回 |
| `Get-ChildItem -LiteralPath *.moc3` 匹配不到 | `-LiteralPath` 不展开通配符 | 用 `-Path`（或先 `Get-ChildItem -Recurse` 再筛） | 实测 |
| 网页加载 `.moc3` 却能跑 | `server.mjs` 的 MIME 表没有 `.moc3`，回落 `application/octet-stream` | 不用改：Cubism 按二进制读，不看 MIME | 4096 渲图成功 |

**三墨映射（外部必须先做，再交引擎）**：引擎的 `_prepareInk` 会把任意彩色图"就近折到两个墨"，青蓝发会被折成米白、与皮肤粘成一块。所以在喂进片子之前，用 HSV 规则自己定语义：`v<0.30 → 黑`（线稿/深甲）；`h 150–265 且 s≥0.12 → 橙`（青蓝发）；`s<0.20 → 米白`（白布/无彩）；`h 5–55 且 s<0.42 → 米白`（皮肤）；其余 → 橙。实测四张的头部分配（cream/orange/black）落在 32–36 / 44–50 / 14–25 %，语义是对的（发→橙、白布与皮肤→米白、深甲→黑）。

**碎斑成因与三档处理**：原画是带渐变的赛璐璐，阈值切在渐变带上就会留下成片小岛（腮红、发际高光、肤色暗面）。

- `--clean` = **5×5 众数清理**遍数（默认 2）：`2` 保留细节、碎斑明显；`10` 把蕾丝/棋格/睫毛熔成大块，形体更"整"但细节全丢。
- `--block N` = **两段式"只取形体"**（后加）：① 先降到 1/N 宽，按格做 HSV 分类，细节在降采样里被平均掉；② **每个墨层单独**用平滑放大放回原尺寸，再按 `alpha≥128` 阈值取形——边缘是平滑曲线，不是马赛克台阶。
  - 第一版（按格放大回原尺寸、最近邻）在 block 8/16/32 上是**更难看**的马赛克台阶，废掉；改成"分层平滑放大 + 阈值"才对。
  - 实测 block 40（2172×2896 输出）：cream 37.3% / orange 39.8% / black 23.0%，bbox 1849×2736 @(323,160)，留白 上 5.5% / 左 14.9% / **右 0.0%** / 下 0.0%。眼睛、花饰、棋格、蕾丝全部消失，只剩发/脸/衣/甲的块面。
- `--keyline` = 沿 alpha 内缘加黑边（输出 px，默认 6；block 模式用 10 才看得出）。

**720p 实片观感（关键证据）**：`--art <目录>` 换一套剪影目录（`?art=` 同步加在 `src/main.js`，`--art` 加在 `export/export.mjs`），把新 `f_bust` 与另外七张原图混在一套里渲 8 / 12 / 20 / 30 秒：

- `clean 2`：帽子、棋格披风、蕾丝在 720p 下变成**成片噪点块**，比原图更"吵"。
- `clean 10`：噪点没了，但糊成一坨，帽子只留方块轮廓，裁切偏心（右留白 0%）。
- `block 40`（只取形体）：**暗底里读成柔和的橙/米白色块**，比 clean 2 干净、比 clean 10 有形，是三档里唯一能当背景看的。证据 `out/_ref/cmp_sil.png`。
- 结论修正：**"只取形体"版可作占位/试验，仍不能直接当成品**。差的不是画质而是三件事：
  1. **构图贴右**：`pad 0.78` 重渲后 bbox 右留白仍是 **0.5%**——模型绘制区本身超出画布矩形，pad 管不到，只能在 `render.html` 里用 `ox` 平移。
  2. **没有面部**：无脸符合原片口径，但脸现在只是一块米白，眼窝/鼻梁的形都没了，正脸段会显得空。
  3. **配准没对**：`regions.json` 与 `REGISTER` 是按原片 `f_bust` 的三点（下巴/花饰/领口）定的，这套图的构图基准不同，特写段（166.5 / 170.19 秒）一定偏，必须重测 `art_check`。

**裁切与配准的坑**：`ink` 的 `--crop` 是**源像素**，缩放后坐标要重算；默认姿势头是偏的（`ANGLE_X=-30`），直接居中会切到右边。三次实测留白：`310,140,1050,1400 → 左34%/右0%`、`910,300,1520,2027 → 左34%/右0%`、`1200,330,1600,2133 → 左14.7%/右0%`——**右留白一直是 0**。把 `pad` 从 0.92 降到 0.78 重渲（画布 3195×3195 @213%），全图 bbox 2678×3404 @(1397,692)，右留白仍只有 **0.5%**：模型的绘制区本身就超出画布矩形，**pad 管不到，只能改 `ox` 平移**。

### 3.5 高清化与裁剪：改成"在 Live2D 里按框渲成品尺寸"

**先算清坐标基准**（后面所有换算都靠这两条）：

- 模型画布是 **1500×1500**（`model.width` 在 `scale=1` 时就是 1500；`1884×1884` 是 `pad 0.92` 下 2048 画布的显示尺寸，别当模型原点用）。
- 4096 画布 @`pad 0.92` → `s = 4096×0.92/1500 = 2.512`，模型中心落在画布中心 2048：
  **`model = (imgPx - 2048)/2.512 + 750`**；反向 `imgPx = (model - 750)×2.512 + 2048`。
- 校准法：`render --w 1500 --h 1500 --pad 1`（此时 `s=1`，输出像素**就是**模型坐标），再 `ink --dry --block 1` 读 bbox。实测 l2d16 全身 bbox `710×1387 @(444,113)`，与上面反算的 `444 / 113` 完全对上，说明换算与 y 方向都对。

**`?box=x,y,w,h`（模型坐标取材框铺满画布）**：上一版出空白图的真因不是方向，是 **`model.width` 会随 `model.scale` 变**——公式里用它算中心，等于拿"缩放后的 10229"当"画布 1500"。修法：`const mw = model.width, mh = model.height;` 在任何 `scale.set()` **之前**存下来，再算 `model.x/y`。着色器不用改，一次就对。

**成品尺寸直渲**：`--box 412,66,637,849`（637:849 = 3:4）@ `4344×5792`（2× 目标），再 `ink --w 2172 --h 2896`（`crop whole`，只做一次降采样）。相比"4096 全身图裁 1600×2133 再放大到 2172"，**信息量不变**（纹理图集 2048 就是上限，胸像天然只有 ~1160 px），但少了"裁 → 放"两道双线性，边缘不叠台阶：`out/_ref/edge_ab.png` 里左边（裁放）是方块状硬棱，右边（直渲）是圆滑曲线。

**3:4 的几何硬限制**：全身宽 **923 模型单位**、胸像高 **802 单位**；3:4 框要么按宽定（`w=923 → h=1231`，会框到腰以下），要么按高定（`h=802 → w=601`，披风被切）。**按胸像高定框时左右一定贴边**——这不是裁剪参数没调好，是形体比例和 3:4 不合；想要左右各 5% 留白，只能把框放宽到 `w≈1000`，那时头会缩到画面 1/4 以下。原片 `f_bust` 自己也是 bbox 1079/1086 ≈ 满幅，同理。

**进片实测（`--keyline 0`，block 40，`out/_ref/cmp_sil3.png`）**：8 秒左下大块暗形、12 秒右侧贴边一条、20 秒右侧橙色竖条、30 秒几乎看不见。**能被看见，但读不出"人"**——还是配准问题：`regions.json` 的取景框是按原片 `f_bust` 的构图定的，这套图的头/胸位置不同，画进去就滑到画面边缘。

**留下的东西**：`assets/live2d/{l2d16.u,l2d01.u,l2d04.u}`（三套，含第三方版权，**绝不可发布**）、`tools/live2d_art.mjs`、`tools/live2d_lib/`、`out/_ref/plate4096.png`（4096 透明渲染 @pad0.92）、`plate4096_p78.png`（@pad0.78）、`calib.png`（1500 @pad1 校准图）、`bust_ss.png` / `bust_ss2.png` / `bust_ss3.png`（按框直渲 4344×5792）、`bust_b20/b40/b40k0/b40m.png`（2172×2896 成品）、`sil2_b40.png`（裁放版）、`edge_ab.png`（100% 边缘对比）、`cmp_old.png` / `cmp_new.png` / `cmp_sil.png` / `cmp_sil3.png` / `f20_flat.png`（进片并排）。

### 3.6 三点配准与特写段验收（结论：166.5 判不过）

**锚点从 `regions.json` 来**（原片 `f_bust` 的设计px，除以 1086/1448 归一化）：

| 锚点 | 原片 px | 归一化 |
|:--|:--|:--|
| 下巴 `chin` | (571, 628) | (0.526, 0.434) |
| 花饰 `flower` | (760, 217) | (0.700, 0.150) |
| 胸针/领口 `brooch` | (574, 797) | (0.529, 0.550) |
| 头顶（bbox） | y≈16 | 0.011 |

**在模型坐标里量同一批点**（校准图 `calib.png` 上量）：头顶 **113**、下巴 **631**、领口 **694**（模型单位）。

**按"头顶 1.1% + 下巴 43.4%"反算取材框**：头高 518 单位 = 42.3% 画面高 → `h = 1224`、`w = 918`；下巴落在 43.4% → `y0 = 631 - 0.434×1224 ≈ 100`；下巴 x 对齐 0.526 → `x0 = 838 - 0.526×918 ≈ 355`。得到 **`--box 355,100,918,1224`**。

**验收结果（`art_check`）**：位移从 133 px 降到 **10 px**（位置完全对上），但**尺度差仍 25.3%**，`fw` 0.742 vs 原片 0.994——这套模型没有横向铺开的长发，宽度注定填不满 3:4。**这不是参数还能调出来的，是形体本身。**

**特写 166.5 秒判不过**（`out/_ref/cu_ab3.png`：原片 / 配准版 / 紧框版三列）：

- 原片在那个镜头里读成"人"，靠两件事：**横向铺开的橙发**当外框，**纯黑的脸**当内芯。
- 这套三墨化之后是**竖条色块**：帽子在上方撑出一块黑，肩膀窄，脸是米白 → 镜头自带的提亮 + RGB 色散把米白直接打过曝成白团。
- 补救了两种，都没救回来：`--skin black`（皮肤走黑，贴"无脸"设计）→ 头顶那块米白（帽/花饰）反而变成主体；`PARAM_ANGLE_X/Z=0` 把 3/4 侧头转正 → 形体更散。
- 170.19 秒那个镜头反倒两边接近（都是抽象特写，看不出人）。

**结论**：这套素材的能力上限是**"暗底背景里的柔和色块"**（8 / 12 / 20 / 30 秒能用），**不是能露人的胸像特写**。要顶特写，得换服装（长发的私服/女仆）或等画师。

### 3.7 换路子：不做图，做滤镜（`tools/art_filter.mjs`）

**动机**：规格要八张图，供给却是"没画师、上游无设计稿源文件"。中间的差不该靠**描**来填——片子要的从来不是"某一张画"，而是**这套三墨语言**；语言可以做成一层滤镜，任何输入都能收敛进来。

**实现（`tools/art_filter.mjs`，新工具）**：

1. **cover 到目标尺寸**（短边铺满、长边居中裁，绝不拉伸；3:4 / 1:1 都是这样保证的）；
2. **双边平滑**（`--smooth n` / `--sig σ`）：按亮度差加权，纹理（毛孔、渐变、压缩块）被压平，**边界不动**——这一步是 block 方案里缺的，block 是降采样把边界也平均掉了；
3. **分墨**：`--mode hsv`（默认，语义规则：发→橙、白布/无彩→米白、深色→黑、皮肤 `--skin cream|black`）或 `--mode k3`（明度三分，给没有色相语义的照片/截图兜底）；
4. **3×3 众数清理**（`--clean n`）去碎斑；
5. **小连通块剔除**（`--min-area px`），2172×2896 建议 300~800；
6. 出 **PNG-24 三墨、主体 alpha 255 / 外部 0**，直接符合规格单。

**与 `--block` 的本质差别**：block 是"降采样只留大块"，细节（眼睛、发丝、盔甲缝、蕾丝）全没了；滤镜是"按语义分墨 + 保边平滑"，**细节保住**，也不出方块台阶。

**实测（Live2D 全身直渲图 → 2172×2896，`out/_ref/f1_bust.png`）**：cream 33.7% / orange 42.4% / black 23.8%，bbox 1618×2864 @(271,32)，留白 上1.1 / 左12.5 / 右13.0；`art_check`：`cx` 0.4972、`cy` 0.5055（原片 0.5014 / 0.5035，**位置对上了**），`fw` 0.7449 仍差 25%（形体本身窄，与滤镜无关）。

**进片**：166.5 秒特写**终于读得出"人"**——头、帽子、脸、臂甲都在（`out/_ref/cu_filter_ab.png` 右）；8 / 12 / 20 / 30 秒在暗底里像"她站在后面"（`out/_ref/cmp_filter.png`）。比 block 版的竖条色块强一档。

**还没解决的**：脸是米白，原片是**纯黑的脸**；要走原设计就加 `--skin black`（这一档在滤镜下比在 block 下更耐看，因为保留了眼睛的形）。

**用法**：

```powershell
node tools/art_filter.mjs --in out/_ref/bust_reg3.png --out out/_ref/f_bust.png --w 2172 --h 2896 --min-area 400
node tools/art_filter.mjs --in 任意图.png --out out/x.png --mode k3 --smooth 3 --clean 2 --min-area 600
node tools/art_filter.mjs --in assets/character/f_bust.png --out out/_ref/rt.png --w 1086 --h 1448 --dry
```

### 3.8 「颜色不够用」：多阶预览能救到什么程度

阁下一句**"颜色不够用"**，点到了三墨的极限：皮肤、衣料、盔甲在滤镜下并成同一块，**层次和色相区分度都没了**。先量、再判：

**先说做错的一版**：第一版多阶是"在整个 黑→橙→米白 区间等距插值，按 RGB 最近色阶重贴标签"。结果**色相语义丢了**——橙色的头发被贴成米白（因为它亮），跟"三墨分族"的语义规则对不上。

**改对的做法**（`art_filter.mjs --levels N`，N>3）：**先按语义分三族（黑 / 橙 / 米白），再在族内按亮度分暗→亮的阶**：

| 族 | 阶（暗→亮） |
|---|---|
| 黑 | `#141010` → `#241a15` |
| 橙 | `#8f3a1e` → `#dc723f` → `#f09060` |
| 米白 | `#d9bb98` → `#f4e0c6` |

合计 7 阶，族内用亮度分位（每族各自的 min/max 三等分）落阶。实测同一张 Live2D 图：1:8.1% / 2:15.5% / 3:22.4% / 4:8.6% / 5:11.2% / 6:0.8% / 7:33.4%，**橙发回来了、棕甲分出来了、白衣亮了**。

**一个坑（值得记）**：族内分阶时如果边改 `label` 边读 `label` 判断族别，黑族暗阶（标签 1）会被米白族当成自己的像素改写掉——**必须先 `fam = label.slice()` 存族别**。第一版就是这么错出"黑 0%"。

**但要说清楚**：`--levels` 只是**看效果的预览**，它产出的图**超出规格**（规格是三墨 ±12，引擎 `_prepareInk` 也只会把任意图**最近两墨折叠**成三墨）。真要走多阶，是**引擎层的改造**：

| 方案 | 改什么 | 代价 | 代价之外 |
|---|---|---|---|
| **A. 扩墨 5–7 阶** | `_prepareInk` 从"三墨折叠"改成"族内分阶 + N 张掩膜"；`INK_RGB` / `INK_KEY` / `halftone` 的 `ink` 参数扩容；规格单三墨 → N 墨；`art_check` 与 `baseline.json` 同步 | 引擎半天到一天，之后全片回归（1080p 一趟约 55 分钟） | **偏离原片的三墨气质**——原片就是三色印刷，多阶会更像普通插画 |
| **B. 三墨 + 网点** | 不动引擎，用现成的 `art.halftone()`（`ink` 可指定"只在某一墨打点"）在特写镜头补一层网点中间调 | 改场景参数即可，1–2 小时 | 只加**明暗层次**，不加色相；观感是"印刷网点" |
| **C. 三墨维持** | 什么都不改 | 0 | 平，当占位图用 |

**雪翎的判**：这批素材的毛病不是"墨少"，是**形体不像**（宽度差 25%、脸是米白而原片是纯黑）。扩墨能把"颜色不够"这一条消掉，但救不了"不是同一个人"。若刻本片原气质，B 更划算；若阁下更在意"看着像插画"，走 A。**等阁下定，雪翎再动手**。

### 3.9 落地：扩墨（阁下选了 A）

**口径**：三墨不是唯一合法答案了。**画得出来的可以交三墨；画不出来、只能拿别人的图过滤镜的，可以交七阶**。引擎两条都认，同一套坐标基准。

**七阶表**（照色族排，浅 → 深；三墨就是第 0 / 3 / 5 阶）：

| 阶 | 族 | 值 | 用途 |
|---|---|---|---|
| 0 | cream | `#f4e0c6` | 米白主体（= 原三墨的 cream） |
| 1 | cream | `#d9bb98` | 米白的暗面 |
| 2 | orange | `#f09060` | 橙的亮面 |
| 3 | orange | `#dc723f` | 橙主体（= 原三墨的 orange） |
| 4 | orange | `#8f3a1e` | 橙的深面（铁甲、影） |
| 5 | black | `#241a15` | 黑主体（= 原三墨的 black） |
| 6 | black | `#141010` | 黑的更深 |

**引擎改了什么**（`src/engine/art.js`）：

1. `_prepareInk` 除了原来那三张累积掩膜，**再算一层"族内分阶"**：先按三族规则分族（跟原来完全同一套 `C1/C2` 判断），族内按亮度把实体分成 cream 2 / orange 3 / black 2 阶，存成 7 份覆盖率 `level.cov`。
2. **三墨路径一个字没动**：`mask` / `path` / `exact` / `label` 全部照旧，所以八张原图渲染与改动前**逐像素不变**（七阶 art 用不到的老接口也照旧能跑）。
3. 新增 `art.shades(name)`：列出这张图实际带了哪几阶（份额 >0.4% 才算），给场景决定要不要多印。
4. `art.inks()` 的 plate 支持 `{ ink:'cream', shade:1, tint:0.72 }`：按"该阶累积掩膜 − 下一阶累积掩膜"取精确区域，颜色用 role 色 ×`tint` 压暗，**不新增调色板角色**。
5. 明暗阶走**位图**（惰性建掩膜 `_levelMask`），不进 `trace` 轮廓：特写转 path 时明暗阶自动跳过，三墨路径仍然负责轮廓锐度。

**场景改了什么**（`src/scenes/climax.js` 的 `figure()`）：三张主 plate 之后，若这张图带暗阶，再叠 `cream 1 / orange 2 / black 1` 三张暗面（tint 0.72 / 0.62 / 0.8）。`shades:false` 可关。

**验收**：

- `art_check` 加 `--levels` 测量（`LEVEL_SEEDS` / `palette` / `levels` / `outsidePct7`）：七阶版实测 `palette 7`、阶分布 33.4 / 0.8 / 11.2 / 8.6 / 22.4 / 15.5 / 8.1、**outside 0%**，构图 `cx 0.4972 cy 0.5055 fw 0.7449`。
- 进片（166.5 秒，1600×900）：七阶版比三墨版多出**铁甲的暗面、发丝的层次**；三墨版那块是平橙。
- 进片（20 秒，暗底剪影）：**几乎看不出差别**——图被画得很暗、又压了一层 UI 遮罩，暗阶全被吃掉。结论：**扩墨只在"露人"的镜头值钱，暗底当背景色块的镜头不值得**。
- 三墨原图回归：同时间点渲染与改动前**肉眼无差**（163.5 / 185 两帧比对）。

**代价**：每帧多印 3 张掩膜（7 张/帧对 3 张/帧），全片导出速度会掉——**未实测**，等整个美术层定稿再量。

**还没做的**：七阶规则没有进入 `regions.json` / `REGISTER` 的重测；4K 母版未跑；`assets/character` 里仍是三墨原图（七阶只存在于 `assets/_test_art` 的试验位）。

### 3.14 片尾压平：换的不是"覆盖层"，是她自己的墨（2026-11-18，已修）

**症状**：`down-power`（203.42 s 起）里她的头被压成无五官灰板之后，画上仍浮着一层苍白，跟着构图走，越到片尾越明显（205.1 s 最刺眼）。

**根因**：`flatFace()` 是"在她身上再印一层头形 matte"，透明度按 `alpha^0.35` 算。她的本体是 `0.75*fade` 在掉，这层却被三次根号托着不掉——205.1 s 时 `fade≈0.36`，本体 0.27、覆盖层 0.66，**覆盖层比她本体亮 2.4 倍**，所以它读起来是贴在脸上的苍白片，而不是她。

**修法**：不再叠覆盖层，改成**在同一张板上换墨**——她的画 `0.75*fade*(1-k)`，她的纯剪影 `0.75*fade*k`（`art.silhouette`，无 crop，整身）。两者亮度同源同量级，交接处没有第二种颜色，也没有第二套变换：

- `figure`（`glassFigure`）：`0.75*fade*(1-kFace)`
- 新增 `flatSelf(ctx, kFace, 0.75*fade)`：`art.silhouette(ctx,'f_bust', GLASS_FIG, {color:'mute', alpha})`

**验收**（`out/_scan/`）：

- 帧：`tail5.png`（203.6／204.0／204.6／206.0）——203.6 还有眼睛，204.0 起只剩单色形；`tail4.png`（203.9／204.3／204.8／205.15）——205.15 仍是干净的一片形，无贴片边缘。
- 亮度（同一块脸区取样）：旧覆盖层方案 49–69，换墨方案 33–41，**压平后反而比本体更暗**，不存在"苍白"；R 通道无蓝边。
- 变换：两条路径都用 `q = GLASS_FIG.w/1086 = 0.884`、同一张 `f_bust`、同一 `dx`，**不存在相对位移**（原先"随构图微移"是那层亮片与半透明本体的叠加在视觉上互相拉扯）。

**代价**：多印一张整身剪影（约 4 s 镜头），可忽略。

### 3.12 无脸化：自动补洞靠不住，`--erase` 才是出口（2026-11-17）

片子要的是**无脸**剪影，模型天生有眉、眼、鼻影、嘴。四条路试下来：

| 试法 | 结果 | 原因 |
| --- | --- | --- |
| `--skin black` | 五官仍在墨下面露边 | 只是把皮肤换墨，没抹掉形体 |
| `--block 8` / `12` | 脸被压平大半，眉与眼落成两小块 | 眼比周围暗得多，降采样平均后仍越过分类阈值 |
| `--faceless`（补洞） | **失效** | 头发压着脸，眉眼与头发连通；泛洪从 ROI 边界能穿过去，"洞"判不出来 |
| `--erase x,y,w,h` | **有效** | 由人给框，工具把框内实心像素填成皮肤墨（多块用 `;` 分隔） |

有效的那一条（724×966 胸像）：

```powershell
node tools/live2d_art.mjs ink --in out/_lib/p_front.png --out out/_lib/i_front_face.png `
  --w 724 --h 966 --crop 772,189,633,844 --block 6 --clean 3 --keyline 4 --erase "420,505,152,122"
```

`--erase` 在 keyline 之前执行，所以抹掉的区域不会再被勾出内线。**但框里的透明小洞必须一起堵上**——
第一版只填实心像素，眼白/眉间隙的透明洞留着，keyline 又会沿洞边勾一圈黑，看上去像"抹不干净"。
现在 `--erase` 会把框内左右有实心像素的透明像素一并填成皮肤墨，724×966 实测框内残留 0。

**结论**：无脸是设计决定，不是算法问题。工具负责"给了框就抹干净"，框由人给——这和 §二 那套"三墨是语言、不是滤镜"是同一件事。

### 3.13 压墨的上限：处理 ≠ 设计（2026-11-17）

阁下判「出来的效果全都不可用」，判得对。把四版并排看，差距不在参数：

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| 原片 `f_bust` | 画师按曲子的三墨语言**设计**：长发流向、领结几何切面、脸是纯黑空块 | 干净、能一眼记住 |
| 上一版 | `--block 4` 压墨 | 到处碎斑，像矢量化失败 |
| 全分辨率分类 | `--block 1`，靠分辨率换平滑 | 边缘顺了，碎斑仍在（蕾丝、花纹、发高光） |
| 去碎块 + 堵洞 + 抹眼嘴 | 新增 `--island`（小色块并回主墨）、透明小洞回填、`--erase`，并调低蓝色阈值 `--blue 0.005` | 顺眼多了，但仍只是「插画被压平」 |

**结论（要写进判断里）**：自动压墨永远到不了原片标准，因为原片是**设计**出来的，不是**处理**出来的。
`--island` / `--erase` 能把"处理"这一侧做到干净，但"哪块该是什么形"这一侧，只有人能定。
所以这条线的定位只能是**占位稿**：先用它把八张换进片子看构图与节奏，发布前仍由画师出正品。
状态：`--block 1 --clean 2 --island 12000 --keyline 4 --blue 0.005` + `--erase` 是目前最好的一档（`out/_lib/vJ.png`）。

### 3.10 四张露人图出七阶：两个新坑（2026-11-17）

**坑一：
ender.html 的 &params= 不吃 JSON。** 第一次拿 --params '{"PARAM_ANGLE_X":-32}' 去转侧身，渲出来 bbox 跟 f_bust **一像素不差**——参数被静默忽略，什么都不报。正确格式是**逗号分隔的 名字:值**：--params "PARAM_ANGLE_X:-62,PARAM_ANGLE_Z:0"。

**坑二：参数名是全大写的 PARAM_ 前缀。** ParamAngleX 那套是 Live2D 官方示例的写法，这套模型不是；真名见 out/_ref/dump16.txt（PARAM_ANGLE_X 默认 -30、PARAM_ANGLE_Z 默认 -15、PARAM_EYE_BALL_X 默认 0.8）。写错名字同样静默跳过。

### 3.11 `raw.json` 兜底把整套剪影打死（2026-11-17，已修）

上一轮加「原生立绘」那条线时，`art.js` 的 `loadArt` 写成：

```js
try { art.raw = await (await fetch(`/${dir}/raw.json`)).json(); } catch { art.raw = {}; }
if (!Array.isArray(art.raw)) art.raw = {};      // ← 病根
```

`art.raw` 是**实例属性**，而构造函数里它是 `[]`。没有 `raw.json` 时（当时 `assets/character/`
里就没有）兜底把实例上的 `raw` 换成了 `{}`，于是每一次 `inks()` 走到 `this.raw.includes(name)`
都抛 `TypeError: this.raw.includes is not a function`——**不是某一张坏，是全片每个镜头都画不出剪影**。
1080p60 成片是在这次改动**之前**出的，所以片子没事，但改动之后任何一次导出都会踩雷。

修法：两处兜底都改成 `[]`（空数组 = 没有任何 key 走原生位图，全部按剪影画）。
落点 `src/engine/art.js`。教训：这类"默认值换类型"的坑不会报在改动的那一行，
只在下一个跑到它的人身上炸；**改完装载器必须抽一帧看剪影还在不在**，不能只看退出码。

### 3.12 三张画板丢了 alpha，进片是黑方块（2026-11-18，已修）

`f_bust` / `f_eye` / `f_reach` 这三张当初是走另一条路径落盘的，**存成了 RGB**：
文件里没有 alpha 通道，浏览器读到就是"不透明 + 黑底"。于是凡是用到它们的镜头，
人物周围多出一个方方正正的黑矩形，最明显的是 `EXISTENCE` 那帧（她头顶的黑块）；
`f_eye` / `f_reach` 因为构图本身就顶满画幅，只在内侧角落露黑，反而不容易被看出来。
另外五张（`f_profile` / `boy_bust` / `man_bust` / `cat_bust` / `cat_paws`）是 RGBA 正常。

查法（一眼看出病）：

```powershell
python -c "from PIL import Image; import glob; [print(p, Image.open(p).mode) for p in sorted(glob.glob('assets/character/*.png'))]"
```

`RGB` 就是坏的；`RGBA` 且透明占比 0% 也是坏的。

**试过但不可靠的路**：想从源图（`out/_lib/p_face.png`、`hnl_bust.png`，4096 带 alpha）反推
这三张当时的裁切窗口，再用源图重出一份带 alpha 的。两种量法都失败了——
FFT 全尺度 SSD 匹配的最优倍率一律卡在搜索下界 `s=1.0`，MSE 10000 上下；
改用绿瞳当标尺（源图里双眼可测，画板里双眼按色相也能测）算尺度，
`f_bust` 得到 MSE 4681、`f_reach` 连左右眼都并成一个团（两块同 x）。
结论：**这三张的出处不是这两张源图**（或至少中间还有别的缩放/裁切），反推不成立，放弃。

**真正用的修法**：黑底是**纯黑**（四角 `(0,0,0)`，纯黑占比 42.6% / 40.6% / 16.5%，
非黑像素最暗值 ≥ 7），所以直接从四条边做泛洪，吃掉与画幅边缘连通的近黑像素即可，
人物自身的黑色区块（不与边缘连通）不动；掩膜再做 0.8px 高斯羽化，边缘不平切。

```powershell
python tools/plate_alpha_key.py f_bust f_eye f_reach     # 就地补 alpha，已是 RGBA 的会跳过
```

`--tol` 默认 18，用意是连压黑时被压暗的那圈边（值 7～16）一起吃掉，否则会留一道黑描边。
复核方式：把画板压在**蓝**和**红**两种底色上各拼一格（`out/_lib/alpha_key_check.png`），
再看实际出帧——`EXISTENCE`、`OBJECT CREATION`、`f_reach` 那几帧的黑矩形已消失。

**防复发**：新增 `tools/plate_check.py`（`npm run check:plates`），按 `raw.json` 逐张检查
"是不是 RGBA + 透明占比是否 > 0.1%"，不合格列出名字并给出修法。出片前跑一次。
教训：画板这类"少一条通道"的错，**退出码永远是 0**，只能靠自检和肉眼压底复核。

### 渲图与画板：参数必须和 PNG 一起落盘

八张画板当年靠"记着的取框参数"裁出来，等到要按 5760 重出时，参数早就不在了——结果
反解出来的画板与文档记载的套装**全部对不上**（`boy_bust` 实际是红夹克 `l2d20`，不是文档写的私服），
一整天都花在认人上。

**从现在起**：`node tools/live2d_art.mjs render` 渲完会在 PNG 旁边写一份同名 `.json`——
模型目录、画布、pad/zoom/ox/oy、motion/t、包围盒、bboxW、顶端比例。画板用
`python tools/plates.py cut --render <渲图> --name <画板名> --zoom/--top` 裁，顺手把
`assets/character/<画板名>.json` 留档；`plates.py native` 就是台账。
旧画板没留参数时才用 `plates.py refit` 反解，并且**看分数**：`<5` 同一构图，`>20` 是另一回事。

导出侧的两个小坑：整片导出**别把 stdout 接管道**（`| Select-Object` 会掐断子进程，看起来像"渲染崩在 8940 帧"），
日志直接 `*> out/_lib/exp.log` 落文件；页面级偶发崩溃（`exportRange` 抛错）重跑一般自愈。
